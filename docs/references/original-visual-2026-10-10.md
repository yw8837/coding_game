## 새 동네 코딩 게임에 적용할 원리

아래는 실제 관찰을 바탕으로 한 설계 제안이며, 원본의 구현을 테스트해 얻은 사실이나 현재 앱에 이미 구현됐다는 주장이 아니다. 화면 디자인, 명칭, 캐릭터, 사건, 미션, 도구 명령, 해킹 소재는 적용하지 않는다.

1. **의뢰인이 원하는 결과를 먼저 보여 준다.** 동네 가게의 영수증 정리, 주민 행사 명단 검증처럼 새 게임만의 생활 문제를 대화로 받고, 입력 자료와 성공 조건을 가까이에 둔다. 근거는 09:00 메일 의뢰와 43:00 요구사항 질문 흐름이다.
2. **작업 상태로 목표를 갱신한다.** 파일을 만들었는지, 실행한 결과가 조건을 만족하는지, 결과물을 제출했는지를 각각 검증하고 체크한다. 01:25–01:35의 진행률과 체크 변화, 52:00의 첨부·상대 반응이 근거다. 코드 입력이나 실행 버튼 누름만을 완료 조건으로 삼지 않는다.
3. **완료를 사람의 변화까지 연결한다.** 결과 파일의 미리보기와 전달 확인 후 의뢰인이 실제로 도움이 된 점을 말하고 다음 단계가 열린다. 52:00과 58:00처럼 상태를 대화에 반영하되, 캐릭터와 문구는 새로 만든다.
4. **첫 출시의 현재 목표는 짧게 유지한다.** 04:35와 단계 변경에서 목표가 짧아지는 장점을 취한다. 02:30, 48:00, 1:40:00처럼 긴 목록이 현재 작업을 밀어내는 모습은 피한다. 과거 작업은 접힌 기록으로 두고 지금 할 일과 성공 조건을 우선 보인다.
5. **실패는 고칠 수 있는 결과로 보여 준다.** 14:00과 1:16:00의 사용법 출력처럼 오류 바로 옆에 입력 위치와 고칠 조건을 안내한다. 새 게임에서는 코드 줄·테스트 사례·예상 출력으로 바꿔, 생활 문제를 해결하는 학습에 연결한다.
6. **작업 자료를 같은 공간에서 읽게 한다.** 코딩 편집기, 결과 미리보기, 의뢰 대화, 작은 자료 패널의 연결을 우선한다. 20:00의 표, 45:00의 관계 맵, 1:04:00의 파일 뷰어는 자료 유형에 맞춘 표현의 근거다. 모든 도구 창을 동시에 띄우는 복잡도까지 가져오지 않는다.
7. **다음 행동을 기억에만 의존시키지 않는다.** 25:00 이후의 수동 메모와 1:30:00의 긴 누적 기록은 플레이어가 정보를 유지해야 하는 부담을 보여 준다. 새 게임은 대화에서 받은 요구사항·작업 파일·제출 상태를 현재 의뢰 카드에서 다시 볼 수 있게 한다.
8. **가독성을 일찍 확보한다.** 1:18:00의 글꼴·크기 설정은 텍스트 작업의 중요성을 보여 준다. 기본 글자 크기, 충분한 대비, 읽기 쉬운 결과 표, 키보드 포커스를 첫 출시부터 확보한다.

## 이 자료로 주장하면 안 되는 것

- 원본 전체를 연속 시청하거나 음성까지 검증했다는 주장.
- 영상 편집의 빨간 확대 상자, 방송 채팅, 얼굴 화면을 게임 UI라고 하는 주장.
- 빈 답장·작성 중 메일·송금 준비·실행 중 화면을 완료로 판정하는 주장.
- 작업 카드와 표가 있다는 이유만으로 자유로운 복수 해법, 모든 분기, 모든 보상 규칙을 확인했다는 주장.
- 1:44 이후의 방송 총평을 게임 최종 엔딩으로 보는 주장.
- 이 화면 관찰만으로 원본 코드 구조·네트워크 구현·상태 저장 방식까지 알아냈다는 주장.

핵심 근거는 대화로 문제를 받고, 실제 자료로 작업하며, 결과물을 전달하고, 의뢰인 반응과 다음 목표로 이어지는 화면 연결이다. 새 게임은 이를 독자적인 동네·코딩 과제·캐릭터·시각 언어로 설계해야 한다.
